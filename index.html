図A　7つの層

Claude Code を、7つの層で動かす

個人で使っている Claude Code の構成図です。設定ファイルを置くだけでなく、会話をまたいで記憶を残し、区切りごとに記憶を整理し直し（この構成では「睡眠」と呼びます）、専門エージェントや外部モデルに仕事を振り分け、Claude Code 自身の設定を点検する仕組みを、7つの層に分けて組んでいます。層を選ぶと、その層の役割と実例が開きます。

わかりやすく説明できていたら嬉しいな──《案内役》モネ

会話のたびに、この7つの層が連携して動きます。層は上から、土台 → 記憶 → 自動制御 → 実行 → 外部モデル → 運用 → 判断の順に並べています。一般的な設定と最も違うのは、3番目の層「自動で動くしくみ」（中核）です。

層 01

静的設定

毎回読む土台・ルール

会話のたびに必ず読み込む土台です。実行してよい操作・委任の方針・モデルの使い分けをルールとして定義します。待機中の助っ人AI 101体のカタログのような件数の多い一覧は、常時は読み込まず、必要なときだけ読みます。

  • CLAUDE.md（目次）
  • AUTHORITY（判断基準）
  • 委任ルール
  • モデル選択ルール
  • 外部ワーカーの境界

実例

CLAUDE.md
## 決裁経路 / サブエージェント運用 / モデル選択
@~/.claude/rules/AUTHORITY.md
@~/.claude/rules/subagent-delegation.md
@~/.claude/rules/model-routing.md
# 待機101体のカタログは重いため @import せず、必要時に Read（オンデマンド）

なぜ：毎回読むものは、そのぶんコンテキストを消費します。件数の多い一覧まで常時読み込むとコンテキストが圧迫され、ルールを正しく参照できなくなるため、必要なときだけ読み込みます。

層 03・中核

自動で動くしくみ

注入・安全装置・睡眠

本システムが一般的な設定と最も異なる中核部です。6種類のタイミングで計8本のフック（自動実行される小さなプログラム）が動きます。開始時に人格と看板（作業の状態を並べたタスクボード）を注入し、危険な操作はモデルの判断に頼らずコードで止め、コンテキスト圧縮の直前には「睡眠」（溜まった情報を記憶と看板へ書き出す手順）で記憶を整理します。

  • 開始時の注入
  • 危険操作の機械的ブロック
  • 睡眠（sleep）
  • コンテキスト残量のリマインド
  • 委任モデルの実測ログ

実例（フック）

settings.json
"hooks": {
  "SessionStart": [{ "command": "python3 ~/.claude/scripts/session-start.py" }],
                               // 人格と看板の現状を開始時に注入
  "PreToolUse":   [{ "command": "python3 ~/.claude/scripts/pre-tool-guard.py" }],
                               // 「常に赤」の操作を exit 2 で物理的にブロック
  "UserPromptSubmit": [{ "command": "python3 ~/.claude/scripts/context-pressure.py" }],
                               // 文脈の残量が減ったら1回だけリマインド
  "PreCompact":   [{ "command": "~/.claude/hooks/pre-compact-sleep.sh" }]
                               // 圧縮の直前に「睡眠」を促す
}

なぜ：フックはモデルの判断に依存せず、指定タイミングで必ず実行されます（決定論的）。確実に実行したい処理は、守られるかどうかがモデル次第になる自然言語の指示には書かず、フックに置いています。

層 04

実行

作業を担う

実際の作業を担う層です。定型の手順を定めた「スキル」が72個、得意分野ごとの「助っ人AI」（サブエージェント）が起動可能な61体と待機中の101体あります。役割ごとに決めた基本の14体（図C）と、いま主に使う技術に一致する専門AIは確認なしで起動し（緑）、それ以外は起動前に確認します（黄）。スキルには動画（Remotion 12スキル）・小説・TRPGログ・デザイン生成も含みます。

  • スキル 72
  • 助っ人AI 61
  • 待機 101
  • 役割の4階層

実例（サブエージェント委任）

Agent()
// コード変更後、独立した文脈で2観点を並列レビュー
Agent(code-reviewer)      ← "認証まわりの差分をレビュー"
Agent(architect-reviewer) ← "層構成の妥当性を確認"
// 各自の文脈で実行し、結論の要約だけが本会話へ戻る

なぜ：中間の処理はサブエージェント側のコンテキストで行われるため、大量の調査を任せても本会話のコンテキストを圧迫しません。

層 05

外部モデルワーカー

別のモデルへ仕事を振る

Claude 以外のモデルを「ワーカー」として呼ぶ層です。ただし、ほとんどの作業は Claude の中（本流とサブエージェント）で完結しています。外部に任せる先は主に Codex と Gemini の2つで、Codex には実装（GPT-5.6 Luna）と画像生成（GPT Image 2.5）を、Gemini には日本語の文章を任せます。ローカルの Qwen は機密を含む読み取り調査のために用意していますが、実際の出番は少なく、記録上は0回です。quasar・GLM・gemini-probe は検証のために接続しただけで、実運用では使っていません。

  • 委任の大半は Claude 内
  • Codex＝実装＋画像生成
  • Gemini＝日本語の文章
  • Qwen＝機密の調査用
  • 検証用 3本

実例

Agent() → 別モデル
Agent(luna-codex-worker)     ← "このバグを直してテストを更新"         // 外部・区切られた実装
Agent(codex-image-worker)    ← "透過背景のUIアイコンを1枚"           // 外部・GPT Image 2.5
Agent(gemini-worker)         ← "この段落を自然な日本語に推敲"         // 外部・日本語の文章

なぜ：範囲を区切れる中くらいの作業（バグ修正・画像1枚など）を別モデルに任せ、本流（最終判断を担うメインの Claude）の負荷を抑えます。結果は「証拠」であって正しさの証明ではないため、どのモデルが実処理したかを報告に含め、確認していない検査を済んだことにしません。

層 06

運用・自己点検

健全性を保つ

「AIの仕組みは警告なく静かに壊れる」という課題への対策層です。作業を看板（タスクボード）で可視化し、成果物はレビュー用の AI 2体に並行して見せ（重要な判断は2体とも合格するまで）、月次で不要物を整理し、設定の健康診断・常時ロード量の測定・睡眠による記憶の書き出しを定期的に行います。

  • 看板ボード
  • AI 2体のレビュー
  • 健康診断
  • 月次整理
  • 睡眠
  • 判断ルールの監査

実例

ops/board.md
- [ ] [alert] refs: CLAUDE.md スキル索引に design-creator 未記載
  重大度: WARN
  冪等キー: refs:CLAUDE.md-skills-index:8f3ffa6a
  推奨対応: ## スキル に2行追記

なぜ：健康診断が見つけた不整合を看板へ自動登録します。上の例は、実際に健康診断が検出した索引漏れです。

層 07

判断のルール

自律の範囲を定める

全層に共通する線引きです。AIが自ら決定してよい操作・人間に確認すべき操作・絶対に行わない操作を、信号機の色（緑／黄／赤）で区分します。「常に赤」とした操作は最初に判定し、フックがコードでも止めます。

  • 緑 実行可
  • 黄 要確認
  • 赤 禁止

実例

AUTHORITY.md
git status / log / diff                  → 緑（無確認）
git commit / push（通常のブランチ）       → 黄（確認）
push --force to main ／ public への push → 赤（禁止）

なぜ：色は、やり直せるか（可逆性）と影響が AI 自身の作業範囲を超えるか（影響範囲）で決めます。やり直せない操作や影響の広い操作は、モデルが指示を守ることに期待せず、人間の確認を必須にするか実行しません。

覚えている

過去の会話の事実や決定事項をファイルに残し、次回も参照します。

眠って整理する

専門家と外部モデルに振る

仕事の多くは得意分野ごとの専門AI（Claude のサブエージェント）に振り、実装と画像生成は Codex、日本語の文章は Gemini に任せます。

自らを点検する

設定の不整合を定期的に検査し、危険な操作はコードで止め、人間の確認が必要な操作では停止して問い合わせます。

図B

1回の会話で起きること

会話の場面ごとに、決まったフックが自動で実行されます。場面は左から右へ、はじまり → 準備 → 実行 → 睡眠の順に並び、各場面の下にそこで実行されるフックの名前を示しています。

  1. 会話を開く

    はじまり

    人格と看板の現状を自動で注入し、点検を促すリマインドも添えます。

    • session-start.py
  2. 入力時

    準備

    コンテキストの残量を監視し、人格を保つよう促します。

    • context-pressure.py
    • persona-reminder.py
  3. 作業

    実行

    危険な操作をコードでブロックし、委任先とモデルを記録します。

    • pre-tool-guard.py
    • log-agent-model.py
  4. 圧縮の直前・就寝時

    睡眠

    溜まった情報の要点を記憶と看板へ書き出し、設定のスナップショットを取ります。

    • pre-compact-sleep.sh
    睡眠の6手順を見る
    1. 蓄積を走査（scan）
    2. 看板へ反映
    3. 記憶へ書く
    4. ログを書く
    5. 最終実行を記録
    6. 設定を git に保存

睡眠は、論文「Language Models Need Sleep」の考え方を運用の手順で近似したものです。手動の /sleep と、コンテキスト圧縮の直前に実行されるフック（直近の実行から5分以内なら何もせずに終了）の2つの入口から、同じ6手順を踏みます。フックは6種類のタイミングで計8本あり、上の図にはそのうち主な6本を載せています。

モデルの使い分け（重さは難度で決める）

サブエージェントのモデルは、各定義ファイルの宣言（frontmatter）で決まり、この宣言が唯一の既定です。呼び出し側で重いモデルに上げるのは「不可逆・共有物の設計判断」「事実の正確さが致命的」「判断軸が言語化できていない」の3条件のときだけで、軽いモデルに下げるのは自由です。処理する件数が多いことは、上げる理由になりません。下のバーは、起動可能な61体の割り当てです。

sonnet 38haiku 13opus 6
  • sonnet 38体 — 実装・レビュー・テスト
  • haiku 13体 — 探索・中継役（ワーカーの呼び出しを中継する）
  • opus 6体
  • GPT-5.6 系 4体

図C

誰に仕事を振るか

真ん中の本流（メインの Claude）が最終判断を担います。左は Claude のサブエージェント、右は別のモデルに範囲を区切った仕事を1本ずつ任せる外部モデルワーカーです。ほとんどの作業は本流とサブエージェント、つまり Claude の中で完結します。外部に出すのは主に、Codex への実装と画像生成、Gemini への日本語の文章です。ワーカーの呼び出しは軽量モデルのサブエージェントが中継し、実際の処理は各ワーカーのモデルが行います。

実測（委任モデルの実測ログ・9/6〜9/30）：Claude のサブエージェント 36回（general-purpose 17・research-analyst 12 ほか）、codex-image-worker 7回、gemini-worker 3回（3回とも日本語の文章）、luna-codex-worker 2回。qwen-local-worker・quasar-worker・glm-worker・gemini-probe-worker は0回です。

どこへ振るか（早見）— 課題の型を選ぶと、行き先まで線が引かれます

迷ったら Claude のサブエージェントに任せます。

サブエージェント（Claude）

基本の14体 役割の4階層。カテゴリを問わず常に緑
  • Tier 1 ハブ役agent-organizer / business-analyst / context-manager
  • Tier 2 品質保証code-reviewer / architect-reviewer / debugger / error-detective
  • Tier 3 作業refactoring-specialist / api-designer / documentation-engineer / dx-optimizer
  • Tier 4 思考補助research-analyst / project-idea-validator / prompt-engineer
緑
汎用・調査の助っ人AI general-purpose・research-analyst など。調べものの既定の行き先 緑
現役スタック一致 TypeScript / Next.js / Supabase など、いま主に使う技術の専門AI 緑
それ以外の専門AI・待機101体 別置きの棚（agent-library）。必要になったときだけ呼ぶ 黄
本流 opus・最終判断 曖昧な要件・安全に関わる作業・破壊的な判断は本流に残す

外部モデルワーカー 7本（うち検証用 3本）

Codex の2本柱 — 実装と画像
検証用 — 接続しただけで実運用では使っていない

守っている境界

  • 1本ずつは緑同時に2本以上を実行するときは黄（確認）
  • 外部へ出るものを絞る認証情報・鍵・個人データは依頼文に載せない（赤）。機密の調査はローカルのみ
  • 結果は証拠実処理したモデルを報告に含め、報告されていない検査を済んだことにしない
  • 最終判断は本流曖昧な要件・安全に関わる作業・破壊的な判断はワーカーに渡さない

図D

判断のルール — 自律の範囲

AIが自分で決めてよい範囲の線引きです。信号機の色で「自ら決定してよい／確認のうえ実行／絶対に行わない」を区分します。判定は上から順に進み、まず「常に赤」に当たるかを見て、当たらなければ可逆性×影響範囲の表で決めます。どれに当たるか迷う操作は黄（確認）として扱います。

常に赤 — 最優先で評価し、表より先に止める

  • 認証情報の送信・露出
  • 課金・資金移動
  • メインブランチの破壊的 Git 操作
  • 外部への意図しない書き込み
  • ローカルで処理できるファイルの外部アップロード
  • public リポジトリへの push
  • 重要ファイルの削除（設定・CLAUDE.md・認証情報・人格・利用者の記憶）
  • rm -rf・find -delete（承認済みの月次整理だけ例外）

当てはまらなければ、下の表で判定する

自身の作業範囲のみ
共有・設定・プロジェクト
やり直せる可逆
やり直せない不可逆

マスを選ぶと、その色に当たる操作が出ます。

「好きにやっていい」のような汎用的な励ましは、設定やスキルの自己改変の承認にはなりません。応答できない状況（就寝中など）も承認とは見なしません。

ルール自体を監査する（Jev）

書いたルールが曖昧でないかを、TypeSafe の Jev（System One）に判定させて確かめています。ルールを渡して操作ごとに緑・黄・赤を選ばせ、ルールを書いた側の解釈と突き合わせます。作業中の判断には使わず、監査だけに使います。

  1. 段階1

    読解の確認

    表で答えが決まる22問を先に解かせる。ここで読み違えないことを確かめてから次へ進む。

    22/22正解
  2. 段階2

    曖昧さの発見

    表だけでは答えが1つに決まらない問いを解かせ、書いた側の解釈とズレた問いと確信度の低い問いを「ルールの穴」の候補にする。

  3. 結果

    ルールに9項目を追加

    例：public への push を赤に。

    4→0ズレ
    0.21→0.59最低確信度
    9追加した項目

委任先の選び方も、緑・黄で決まります。基本の14体はカテゴリを問わず常に緑、専門AIは「現役スタック」（いま主に使う TypeScript・Next.js・Supabase など）に一致すれば緑、それ以外は黄です。図C の委任の階層へ戻る
